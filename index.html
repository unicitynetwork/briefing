Sphere28 PRs merged
Analytics rerouted: GA4 server-side, no client tags
PRs #461, #462, #58, #19, and #33 collectively remove Google Analytics client-side tags from the wallet origin and frontend apps, replacing them with a server-side relay approach. Frontend page-view events are now sent to sphere-api (#58), which forwards them to GA4 server-side, eliminating direct browser-to-Google calls. This reduces external script exposure on the wallet origin and gives the platform full control over analytics data flow. The change spans the main sphere app, quest frontend, and developer portal, ensuring consistent telemetry behaviour across all user-facing surfaces.
sphere, sphere-api, sphere-quest-frontend, sphere-dev-portal
Self-host fonts, drop Google Fonts dependency
PRs #21, #29, and #34 remove Google Fonts import calls from the UI library, backoffice, and developer portal respectively, replacing them with self-hosted brand font assets. This eliminates a third-party network request on page load, improving privacy posture and removing a potential GDPR touchpoint. Self-hosting also ensures font availability is not dependent on Google CDN uptime or regional accessibility. The change aligns with the broader theme of reducing external dependencies seen across today's analytics and SDK work.
sphere-ui, sphere-backoffice, sphere-dev-portal
Audience filters, org views, quest gating and analytics
PRs #30 and #60 introduce audience filter controls and organisation-level views into the backoffice and API layers. The API change (#60) adds audience analytics endpoints and quest gating logic tied to organisation context, while the backoffice PR (#30) surfaces these as UI controls with consistency fixes applied across related views. Quest gating allows publishers to restrict quest availability based on audience criteria defined at the organisation level. PR #59 also landed a config fix pointing DEVELOPER_PORTAL_URL at the real production domain, a prerequisite for correct cross-service linking in these new views.
sphere-backoffice, sphere-api
SDK v1 removal, IPFS purge, and payments dead-code cleanup
Three breaking refactors from @MastaP stripped significant dead code from sphere-sdk: #706 removed the entire IPFS/IPNS token sync subsystem at −8,608 lines, #703 eliminated the last v1 token remnants bringing the codebase from 7,025 to 6,912 lines, and #702 analysed the PaymentsModule and removed dead payment code reducing it further from 7,179 to 7,025 lines. Separately, @lploom landed concurrent send operations (#698), batch mailbox deposit with a lock-order redesign in wallet-api (#113), and the corresponding SDK-side batching (#700) that collapses multiple sends into one delivery call per batch. Connect compatibility improvements in #705 and #460 now name the specific SDK version and network in refusal messages, with the example app (#21, #22) and Claude marketplace templates (#14) updated to read and quote the version floor correctly. A security fix in #56 stops the integration connection-test endpoint from echoing plaintext bot tokens, and #112 resolves a race condition on concurrent first-create PUT intents that previously returned a 500.
sphere-sdk, wallet-api, sphere-sdk-connect-example
Quest pause/resume endpoint and streak preservation fix
PR #57 gives quest pause and resume operations their own dedicated API endpoint, separating them from the general publish/unpublish flow. The backoffice fix in #32 corrects a bug where triggering Pause was inadvertently calling unpublish, and also prevents canvas saves from incorrectly tripping quest level limits. PR #42 fixes a check-in streak bug where a second check-in quest completed on the same calendar day would break the user's streak rather than preserve it, addressing issue #31 in the H3 milestone. Together these changes make quest lifecycle management more reliable for both publishers and end users.

nostr-sdk-rust: full Nostr stack from scratch
Six sequential PRs from @MastaP bootstrap a new Rust Nostr SDK from the ground up. PR #1 establishes UNIP-01 binding events, resolution logic, and NIP-01 Filter support; #2 adds GitHub Actions CI; #3 implements a relay client with native transport and a live end-to-end DM round-trip test against a deployed relay. PR #4 adds token transfer and payment request/response protocols over Nostr, #5 brings wasm32-unknown-unknown support via no_std with feature-gated std dependencies for browser targets, and #6 caps the week with a multi-relay client and persistent-subscription primitives for reliable event streaming. This SDK forms the Nostr messaging backbone for Unicity's decentralised token and payment flows.

Testnet2 BFT block rate set to 500ms
PR #27 from @jait91 updates the bft-ansible configuration to set the BFT root block production rate to 500 milliseconds on testnet2. This tightens block cadence significantly, allowing the team to observe consensus behaviour and latency characteristics under a faster finality target. The change is scoped to the testnet2 environment, keeping production settings unaffected while stress-testing the infrastructure.
bft-ansible
Classifier threshold calibration and output-forcing rules
PR #82 from @machmode delivers a set of training improvements to the semanticd classifier. Variance fixes stabilise training runs that previously produced inconsistent results across seeds, and per-model threshold calibration allows each model variant to be tuned to its own optimal decision boundary rather than sharing a global threshold. An output-forcing rule is introduced to handle edge cases where the model would otherwise produce out-of-distribution or invalid class outputs, and accompanying tooling changes make it easier to inspect and adjust these parameters during the training pipeline.
